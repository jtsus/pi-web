# Pull requests, deployments and the files view

## The panel and where its data comes from
`components/PullRequestPanel.tsx` is a pinned right-panel tab (the top bar's PR button). It lists either the PRs this chat's agent recorded (`session` scope) or every open PR of the project's repository (`all`), hides merged and closed ones, and shows detail, checks, files and diffs. The agent's extension writes each PR it opens as a `pi.pr` custom entry in the session file (`lib/pr-links.ts`, `lib/pr-types.ts`); there is no side database, so the link travels with the conversation. `lib/pr-server.ts` reads those entries (`getSessionEntries()`), resolves the repository from the checkout's `origin`/`upstream` remote, and talks to GitHub through `lib/gh-api.ts`. Sorting/scope rules and the diff formatting live in `lib/pr-view.ts`. `app/api/prs/**` are the read, merge, close and staging-merge routes. `components/DeploymentsPanel.tsx` is the read-only cluster tab; `/api/deployments` reports each environment's image and ready replicas and `/api/deployments/sync` pushes a branch catch-up.

**Merge is a message to the chat, not a direct API call.** The Merge button asks the selected chat session to do the work (`merge()` in `components/PullRequestPanel.tsx`): it sends a `prompt` command over `/api/agent/[id]` built by `lib/pr-merge-prompt.ts`, with `streamingBehavior: "followUp"` so a busy chat queues it instead of being interrupted. The prompt names the PR, its branches, the method and an example `gh pr merge` command, and requires the agent to merge it, watch the deploy workflow and live rollout, verify the new revision is actually running, and report a failure instead of claiming success. The panel then closes its detail and shows `prs.mergeAskedAgent`; its list drops the PR once the agent merges it. A panel without a selected session refuses with `prs.mergeNeedsChat`. The `/api/prs/[number]/merge` route still merges directly for code that needs it (the button no longer calls it). Close, merge-to-staging and revert-from-staging remain direct panel actions.

## Files view follows the selected session
`components/SessionSidebar.tsx` keeps the effective files cwd. It follows `selectedCwdProp` (`selectedSession?.cwd ?? newSessionCwd`) whenever that **or the selected session id** changes, so a switch from the agents panel or a notification lands the files view on that session's worktree even when the new path equals the last synced one. A manual picker move with the session unchanged is not snapped back (the effect's dependencies do not change); picking another session moves it to that chat's checkout again. The shell's `activeCwd` follows through `onCwdChange` → `handleCwdChange()`, which keeps existing sessions open on a same-project worktree move.
